# PRD — N.O.V.A. 2026 Doctor Agent

> 상태: **v0.2 (10.13)** — 운영 가이드(`docs/GUIDE.md`) 반영
> v0.1 → v0.2 주요 변경: 효율 중심 → **정보수집·의사소통 중심**으로 무게 이동, 진찰 어휘집·설명 분할·기록 충실도 결정 추가, 개발 키트 활용으로 자체 벤치 범위 축소

---

## 1. 목표

가상 환자를 문진·진찰하고 **S·O·A·P 초진 기록(15칸) + 주진단 1개**를 제출하는 Doctor Agent를 만든다.

- **예선 목표:** 고정 모델(gpt-oss-20b) 위에서 *설계*로 차별화 → 본선 진출
- **본선 목표:** 예선 파이프라인과 로그를 그대로 재사용해 파인튜닝 모델로 교체

## 2. 확정된 대회 제약

상세는 `docs/GUIDE.md` 참고.

| 항목 | 내용 |
|---|---|
| 실행 구조 | `run.py`의 `prepare()`(≤10분, 증례 접근 불가) → `client.ready()` → `consult(client, state)`(**≤30분 · 50턴**) → `client.diagnose()` |
| 증례 격리 | 증례마다 새 컨테이너. `session()`은 서버에서 **지난 기록을 주지 않음** → 대화 기록은 우리가 보관 |
| 행동 | `say()` 1~30자·질문 1개(1턴) · `exam()` 진찰 1개(1턴, **거절도 1턴**) · `diagnose()` 0턴 |
| Doctor 호출 | `chat()` — `messages`·`max_tokens`·`reasoning_effort`·`temperature`만 허용. **JSON 강제 불가**, **빈 답(503) 빈발** |
| 모델 변경 | 예선 Doctor가 gpt-6-luna로 바뀔 수 있음 → **temperature 생략해도 동작**해야 함 |
| 한도(증례당) | 50턴 · Doctor 호출 200회 · 입력 50만 · 출력 10만 토큰 |
| 한도(개발 키, 일) | gpt-oss-20b 3,000 · gpt-6.1-sol 100 · gpt-6-luna 500 |
| 서버 환경 | 인터넷 차단 · CPU 2코어 · RAM 8GB · GPU 없음 · 읽기 전용(쓰기는 `/tmp` 512MB, `/output`) · PyPI 휠만 |
| 제출 | 샘플 검증 **하루 10회**(공개 3건, luna 참고 점수) · 공식 평가 **하루 1회**(10.13 오픈, 리더보드 5건) |
| 채점 | 서버에 기록된 대화·진찰을 **글자 그대로 인용**해 판정 + 비공개 루브릭. 진단은 5점 척도. 공식은 gpt-6.1-sol, 최종은 GPT·Claude·Gemini 평균 |
| 금지 | 외부 API 호출, 증례 간 정보 공유, 비공개 증례 학습, 프롬프트 인젝션 |

### 예선 채점과 기본 에이전트 결과 (C01)

| 영역 | 배점 | 기본 에이전트 | 원인 | 우리 대응 |
|---|---|---|---|---|
| 정보수집 | 25 | **3.8** | 결정적 단서 기록 누락, FH·ROS 빈칸, 진찰 6/10 거절 | D8 진찰 어휘집, D10 기록 충실도, 체크리스트 |
| 효율 | 20 | 20 | 30턴 · Doctor 37회로도 만점 | 상한만 관리 (D2) |
| 진단추론 | 15 | 4.2 | 오진(수면제 의존 → 불면증) | D3 감별진단 유지·Replan |
| 안전 | 15 | 11.3 | — | D4 red-flag 레이어 |
| 의사소통 | 15 | **2.0** | 설명 SAY가 30자 초과로 깨짐 | D9 설명 분할 |
| 검사·추적 | 10 | **0** | P 계획 부실 | D10 P 템플릿 |
| **합계** | 100 | **41.2** | | |

**결론:** 점수는 *효율*이 아니라 **정보수집(25) · 의사소통(15) · 검사·추적(10)**에서 갈린다. 단, 효율 만점은 증례 1개·luna가 아닌 sol 채점 결과 1회뿐이므로 스윕으로 확인한다.

## 3. 핵심 결정

| # | 결정 | 근거 | v0.1 대비 |
|---|---|---|---|
| D1 | **벤치 = 개발 키트 + 공개 샘플 형식의 합성 증례.** 로컬 반복은 `develop.py`(환자 모델 자유), 공식과 같은 환자·판정 확인은 `sample.py`(증례당 ~117원), 채점 확인은 **샘플 검증(하루 10회)**. 합성 증례는 공개 샘플의 대본·진찰표·모범 기록 형식을 따라 Claude로 30→100개 생성(생성 코드·프롬프트 커밋). 로컬 채점기는 gpt-6.1-sol(일 100회)로 6영역 루브릭 근사. | 시뮬레이터를 처음부터 만들 필요 없음 | 축소 |
| D2 | **턴 예산: 기본 40, 스윕 30/35/40/45. 남은 턴 ≤ 6이면 마무리 단계 강제 진입.** 효율은 상한 관리만 한다. | 효율 감점 기준 미확인, 정보수집 비중이 더 큼 | 15~25 → 30~45 |
| D3 | **Plan → Execute → Replan 유지. LLM은 계획·상태 갱신, 행동 선택·검증은 코드.** 정지 조건 = (1위−2위 확률 ≥ θ) AND 필수 체크리스트 충족, 또는 턴 예산 도달. LLM 호출은 증례당 ~40회 이하. | 매 턴 "다음 행동"을 통째로 맡기면 반복·형식 오류·진찰 거절(기본 에이전트) | 목적이 비용 절감 → 품질·안정성 |
| D4 | **안전 레이어 = 주호소별 red-flag YAML.** 필수 문진·진찰·배제 질환 정의(초기 15개 주호소). | 안전 15점을 규칙으로 고정 확보 | 유지 |
| D5 | **Self-consistency는 진단 단계에서만, 벤치로 이득 확인 후 켠다.** 계획 단계는 상태표, **SOAP 작성은 전체 대화 원문**을 넣는다. | 효율 여유 있음. 단서 누락은 요약 과정에서 생김 | 상태표 전용 → 원문 병행 |
| D6 | **제출 운영:** 하루 샘플 검증 ≤10회는 기능 확인용, 공식 1회는 "변경 1개"만. 채택 기준은 로컬 벤치 + 샘플 검증 점수, 공식 점수는 회귀 확인. 마지막 2일은 안정화. | 공식 총 10회(10.13~10.22), 리더보드 5건이라 노이즈 큼 | 샘플 검증 추가 |
| D7 | **본선 대비:** LLM 클라이언트 추상화 + 전체 실행 로그(JSONL) 저장. 본선 베이스는 Qwen3-14B 계열 잠정. | 예선 로그 = 본선 학습 데이터·발표 자료 | 유지 |
| **D8** | **진찰 어휘집(`rules/exams.yaml`).** 기관계별로 "구체적 동작 하나" 문구를 미리 정의(예: 심장 청진, 폐 청진, 슬개건 반사, 팔 뻗어 자세성 떨림, 복부 압통 촉진…). LLM은 어휘집 ID만 고르고 문장은 코드가 보낸다. 뭉뚱그림(too_broad)·비진찰(not_exam) 문구는 사전 차단. | 거절도 1턴. 기본 에이전트 진찰 10번 중 6번 거절 | 신규 |
| **D9** | **설명 분할.** 마무리 단계에서 진단 → 원인/근거 → 계획(검사·치료) → 주의사항·응급 징후 → 재방문 기준을 **30자 이하 SAY 4~6턴**으로 나눠 말한다. 템플릿 + LLM 채우기, 30자 검증은 코드. | 의사소통 15점, 채점은 서버 대화 원문 기준 | 신규 |
| **D10** | **기록 충실도.** 환자 답변에서 숫자·용량·기간·빈도는 **원문 그대로** 사실 목록으로 추출해 SOAP에 옮긴다. 15칸 빈칸 금지(물었는데 없으면 "부인함"), 시작 정보(이름·나이·성별)는 코드가 직접 채운다. P는 추가 검사 · 치료 · 처치 결정 · 추적 · 교육 템플릿으로 채운다. | 기본 에이전트: 졸피뎀 용량 누락, 나이 오기, FH·ROS 빈칸, 검사·추적 0점 | 신규 |
| **D11** | **견고성.** 빈 답(503) 지수 백오프 재시도, `request_id` 재사용으로 중복 턴 방지, temperature 선택 인자, JSON 파싱 실패 시 재질문(최대 2회) → 규칙 폴백, 경과 25분 시 즉시 SOAP 작성. | 빈 답 빈발, 모델 교체 가능성, 30분 초과 시 0점 | 신규 |

## 4. 아키텍처

```
prepare()          rules/*.yaml 로드 (예선: 모델 없음)
   │
[시작] session() → 첫 진술 + 활력징후 (이름·나이·성별은 코드가 파싱해 기록에 고정)
   │
   ▼
① PLAN (LLM)       감별진단 3~5개 + 질문 계획 + 진찰 어휘집 ID 목록(JSON)
   │               + red-flag YAML의 필수 항목 병합 + 기본 문진 체크리스트
   ▼
② EXECUTE (코드)   1턴씩 실행 → [턴, 행동, 보낸 문장, 응답]을 transcript에 저장
   │               SAY: 30자·질문 1개 검증 / EXAM: 어휘집 문구만 전송 / 중복 제거
   ▼
③ REPLAN (LLM)     문진 묶음이 끝날 때마다: 사실 추출 + 감별진단 확률 갱신 → 정지 조건 판정
   │   ├─ 미충족 → 추가 계획 → ②
   │   └─ 충족 or 남은 턴 ≤ 6 → ④
   ▼
④ CLOSING (SAY×4~6) 진단 → 근거 → 계획 → 주의사항·응급 징후 → 재방문 (각 30자 이하)
   ▼
⑤ SOAP (LLM)       전체 transcript 원문 + 사실 목록 → 15칸 JSON
   ▼
⑥ VALIDATE (코드)  근거 없는 항목 제거, 빈칸 보정, 숫자 원문 일치 확인, 시작 정보 고정 → diagnose()

가드: 경과 25분 or 남은 턴 ≤ 6 → ④/⑤로 이동
      LLM 실패 → 재시도 → 규칙 기반 SOAP 폴백 (증례당 정상 chat 1회 이상은 반드시 보장)
```

### 디렉터리 구조 (안)

```
run.py                 # 진입점: prepare / consult / run_agent
nova_sdk.py            # 시작 패키지 제공 SDK (수정 금지)
agent/
  llm.py               # chat 래퍼: 재시도·JSON 파싱·temperature 선택
  state.py             # transcript, 사실 목록, 턴·시간 예산
  planner.py           # PLAN / REPLAN
  executor.py          # SAY·EXAM 실행·검증
  closing.py           # 설명 분할 SAY
  soap.py              # SOAP 생성 + 검증
  rules/
    exams.yaml         # 진찰 어휘집 (D8)
    redflags.yaml      # 주호소별 필수 항목·배제 질환 (D4)
    checklist.yaml     # 기본 문진 체크리스트
bench/
  cases/               # 합성 증례 + 생성 스크립트·프롬프트
  judge.py             # 6영역 루브릭 근사 채점기 (gpt-6.1-sol)
  run_bench.py         # develop.py 기반 일괄 실행 + JSONL 로그
docs/  PRD.md · GUIDE.md
```

## 7. 실험 원칙

- 모든 변경은 **영역별 점수**(로컬 벤치 + 샘플 검증)와 함께 기록한다.
- 공식 제출은 하루 1회, **변경 1개씩**.
- 샘플 검증은 공개 3건뿐 → **과적합 주의**, 합성 증례 벤치와 함께 본다.
- 벤치 실행 로그(JSONL)는 전부 보관한다 → 본선 학습 데이터.
- 합성 증례의 생성 코드·프롬프트도 커밋한다(재현성 요구).
- 크레딧·일일 호출 한도(특히 gpt-6.1-sol 100회)를 매일 확인한다.
